# Frontend performance: `saulburgos6/perf-observability` (PR #108) vs `main`

Date: 2026-10-09. Builds: production `next build` + `next start` (Next 15.5.12, React 19.2).
Branch = `7621574` (security-hardening PR #108 + perf-observability), main = `237d1fc`.
Backends: Go, one Postgres container, two DBs (`perf_branch`, `perf_main`), rate limits off.
Data: "heavy" user `heavy@perf.test` seeded via API on both sides (4 accounts, 12 categories,
8 budgets, 3 investments, 3000 transactions over 12 months, about 70 in the current month).
Machine: 12 cores, shared with other agents running backend load tests, so absolute numbers are noisy.
Versions were always interleaved, and the tables show medians.

Tooling and how to reproduce: `perf/frontend/README.md` (copy in `./tooling/`).

> **Setup caveat (real deployment risk).** `npm ci` (npm 11.13) did **not** install `sharp`
> (an optional dependency of `next`). `/_next/image` then silently serves the original file. The
> sidebar/landing logo `public/Gemini_Generated_Image_sbh8m9sbh8m9sbh8.png` is **7.1 MB**, and
> it was downloaded on every page (`total-byte-weight` was 7.7 MB on the dashboard). All numbers below
> were taken after installing sharp. With sharp, the 64 px variant is 222 B, but the first optimization
> of each variant costs about 110 ms of server CPU to decode the 7.1 MB PNG.

## 1. Verdict on PR #108

**No user-facing regression. Overall it is a net improvement on the client.** The costs it adds are on the
server and are small in absolute terms:

| area | branch vs main |
|---|---|
| First-load JS (gzip, app-build-manifest) | **−74 to −91 KB** on every authenticated client page and `/login`, because main shipped next-auth server code (`@auth/core`, `jose`, `oauth4webapi`, `preact`, ≈75 KB gz) to the browser through `lib/base-repository.ts → @/auth`. Dashboard is +1.7 KB. |
| Bytes per page load (LH, mobile) | −160 to −520 KB (e.g. transactions 865 vs 1302 KB, analysis 860 vs 1377 KB). The main cause: main downloads `notifications/history` (137 KB, uncompressed) 2–3× per load. |
| Requests per cold load | −5 to −22 (transactions 77 vs 92; main: 12 `/api/auth/session` + 8 CORS preflights) |
| API dependency depth ("waves") | 2–4 vs 3–10 (main serializes `getSession()` → call for every repository call) |
| Time to data visible (runtime, unthrottled) | equal or better: transactions 369 vs 419 ms, budget 336 vs 376, investments 332 vs 755, dashboard 331 vs 357 |
| Lighthouse score / LCP (mobile) | equal within noise. LCP is better on 7 of 9 pages (transactions 3.77 s vs 4.94 s). Investments is worse (7.08 vs 6.28 s), but runtime does not reproduce it (332 vs 755 ms data visible). |
| HTML/RSC payload | **+25 KB raw / +7.5 KB gz on every document** (full next-intl catalogs, about 60 KB raw, serialized into each page) |
| Dashboard SSR TTFB | 34 vs 27 ms p50 (+7 ms) |
| Proxy per API call | **+2.3 to +3.6 ms p50** over a direct backend call. That is equivalent to main's `getSession()`+call (4.76 vs 4.50 ms for `/account`), but under 8-wide bursts it is 13.8 vs 2.6 ms per request (20.5 vs 9.1 ms per burst), because Node serializes about 1 ms of JWE crypto per request |
| `next start` CPU under light k6 load | 14.8% vs 12.4% of a core at the same page-view rate (≈+20% per page view); RSS 464 vs 381 MB peak |
| Every proxied response | carries a 1.2 KB `Set-Cookie` (the session is re-encrypted on each call) |

TBT is **not** a reliable signal here (see §3). Both versions have a never-ending sidebar animation, and the
SSE stream keeps Lighthouse observing for the full 25 s, so TBT is bimodal (for example, branch transactions mobile
was 21 590 / 261 / 272 ms across its runs).

Every full load also makes **10–12 `_rsc` sidebar prefetches**, and each one runs the middleware's JWE decode.
Main's preflights come from `Authorization` headers to a cross-origin backend with `cors.AllowAll()`, which sends no max-age.

Waterfalls (`runtime/waterfalls.json`):
- **branch/transactions**: session → {`/account`, `/category`, `/budget`, **`/transaction` (no filters, wasted)**, `/transaction?page=1&limit=50…`} in parallel. Then come `me/features`, `notifications/history` (87 KB) and a second session. Then **`me/features` again**, plus an RSC `router.replace` round trip for the URL sync.
- **main/transactions**: every call is preceded by its own `/api/auth/session` (12 total) plus a preflight, giving 10 dependency waves. `notifications/history` (137 KB) is downloaded 3×.
- **branch/budget**: `/transaction?page=1&limit=100`, then **page=2, then page=3, sequentially** (`findAllSimple` loop), i.e. 3 round trips and 87 KB.
- **branch/analysis**: `dashboard-summary` ×2 (current + previous period, legitimate) and `me/features` + history on every load.
- **dashboard** (SSR): the server fetches 6 endpoints; the client only adds `me/features` + `notifications/history`. **No RSC+client double fetch**, but the TanStack cache is never seeded from server data, so navigating to `/app/transactions` refetches accounts, categories and budgets.

- About **9 300 component renders per keystroke**. The top self time comes from the 50 transaction rows (`w` ×1 426 renders, **186 ms**

- Dashboard tab clicks call `router.replace` (`components/common/animated-tabs.tsx`, `updateUrl`): one RSC request per tab click to re-render a dynamic server page.

## 6. Proxy overhead (`proxy/proxy-bench.json`, n=200 interleaved, keep-alive)

| endpoint | direct p50 / p95 | via `/api/backend` p50 / p95 | overhead p50 |
|---|---|---|---|
| /exchange/rate | 0.30 / 0.39 | 2.62 / 3.60 | +2.32 ms |
| /account | 2.09 / 2.58 | 4.76 / 5.98 | +2.67 |
| /category | 1.01 / 1.30 | 3.27 / 4.11 | +2.26 |
| /transaction?page=1&limit=50 | 1.19 / 1.39 | 3.70 / 4.69 | +2.51 |
| /analytics/dashboard-summary | 8.01 / 9.28 | 11.57 / 12.85 | +3.56 |
| /notifications/history (87.5 KB) | 2.06 / 2.80 | 4.92 / 6.38 | +2.86 |
| burst of 8 parallel (per request) | 2.58 / 8.85 | **13.79 / 21.02** | +11.2 |
| burst of 8 parallel (wall) | 9.11 / 11.23 | **20.52 / 25.19** | +11.4 |

- `/api/auth/session`: branch 2.57 / 3.32 ms and main 2.50 / 3.45. Main's real per-call cost is `getSession()` + call = **4.50 / 5.92 ms**
  for `/account`, versus 4.76 / 5.98 via the proxy. Per call it is the same latency, but main also paid a CORS preflight and a sequential dependency.
- Session crypto (in-process, `next-auth/jwt`, 1.1 KB cookie): **decode 331 µs, encode 226 µs**. Each proxied request does
  `auth()` decode + jwt callback + **re-encode and `Set-Cookie` (1 231 B)** (`app/api/backend/[...path]/route.ts:17`), then
  **decodes again** in `getBackendAccessToken` (`lib/server/backend-proxy.ts:87`). That is about 0.9 ms of CPU per request, and it is what makes bursts queue.
- The token-refresh check is a no-op unless the token is within min(5 min, 50% lifetime) of expiry (24 h tokens), so its cost is in the decode.
- Neither the backend nor the proxy compresses JSON (`notifications/history` is 87.5 KB on the wire both ways).
