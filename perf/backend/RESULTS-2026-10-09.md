# Backend performance: PR #108 (security-hardening, 7621574) vs `main` (237d1fc)

Date: 2026-10-09. Host: 12 CPUs, shared with other agents (load avg 1m at run start: median 5.1, range 0.65–16.4).
Postgres 17 (Docker, `pg_stat_statements`, shared_buffers 512MB), backends built from each commit with a
perf-only pprof overlay, k6 v2.3 in Docker. Pool: 25 open / 25 idle conns for both. Rate limiting off for both
(`RATE_LIMIT_ENABLED=false`), `OTEL_ENABLE_STDOUT=false`, `GIN_MODE=release`, `ADMIN_SEED_ENABLED=false`.
DB role `perf` = table owner with **BYPASSRLS** for both versions (see "Validity" below).

Data (identical in both DBs, md5-checked): 201 users; heavy user = 7 accounts (3 DOP, 2 USD, 2 credit cards),
30 categories, 12 budgets, **50,000 transactions over 3 years**, 10 recurring rules, 72 card payments, 8 investments,
3 loans (+36 installments), 3 certificates (+72 payments), 12 plan items, 60 notifications; 200 light users × 200
transactions (90,000 transactions total, 91k audit-log rows).

Tooling: `wt-perf-backend/perf/backend/` (README there). Raw data: `perf-backend/results/` (this directory).

## Validity notes (read first)

- **Pool-exhaustion deadlock (both versions).** `RLSMiddleware` pins a pooled connection in a transaction
  (`rls.go:58`), then the route-group `RequireFeature` middleware queries the plain `*sql.DB`
  (`featureflag.go:12`, used at `:69/78`) and needs a 2nd connection. With 25 such requests in flight all wait
  forever (POST bodies are never read, so client disconnects never cancel the context → permanent wedge).
  Captured in `results/deadlock/goroutines-branch-ccpayment*.txt` (calibration run: 25 sessions
  `idle in transaction`, 753 goroutines parked in auth `FindUserById`).
  **Which numbers are affected:** the hang happened only in the *calibration* run (not used) and in the
  deliberate repros (`results/deadlock*`, `results/vus100/deadlock`). In the 3-round comparison the
  feature-gated `cc_payment` ladder was capped at 20 VUs precisely to stay below 25 in-flight; `run-matrix.sh`
  health-checked after every run and recorded **0 HANG events** — so no branch number in the tables below is
  hang-affected. Consequence: `cc_payment` max RPS (75) is the ladder ceiling under a 20-VU cap, **not** a capacity
  figure; treat it as invalid for capacity and re-run against the fixed build.
- **main also stalls on plain reads under overload** (see deadlock repro): main's repositories mostly query the
  pool outside the request tx, so any endpoint can deadlock. In the matrix this shows up only at steps *above*
  main's max sustainable rate (0 completed requests at dash_summary 250–300, analytics_summary_1y ≥100,
  analytics_monthly 200, mixed 800 in r1). Those steps are excluded from max-RPS by construction.
- **Host suspend:** the machine idle-suspended 20:37:31–21:21:25 during branch r3 `accounts`; that run is
  discarded (`accounts-branch-r3.invalid-host-suspended.json.txt`) and the `accounts` pair was re-run after a reseed.
- **RLS role:** with a role that does *not* bypass RLS, main returns empty results for most reads (its queries miss
  `app.current_user_id`), so equal-work comparison requires BYPASSRLS. RLS-enforced cost was measured at SQL level
  only (the k6 RLS-enforced round was aborted at wrap-up).
- Moderate-load p95 spreads are wide at low rates: a recurring +40–50 ms tail appears on *write* paths at low
  arrival rates on both versions and disappears at higher rates (likely WAL-flush / idle-CPU wake-up effects on
  this host); compare p50s for small deltas.

## 3. Regression verdict for PR #108

**No meaningful regression on reads; small CPU/alloc cost; one real latency regression on card payments.**

- Reads: p50 within ±4% on every heavy read (balances, budgets, analytics, dashboard); max RPS identical within
  ladder resolution. The `+9–14%` on cached transaction lists is ~0.2 ms absolute (extra `id` tie-break sort,
  decimal scan, response buffering).
- Writes: create transaction **+27% p50 (+0.9 ms)** from the new ownership checks (3 extra PK lookups, 2 round trips
  each). Card payment **+171% p50 (5.6 → 15.1 ms) and p95 13 → 69 ms**: the new overdraft guard locks the paying
  account `FOR UPDATE` and then sums *all* of that account's transactions (`funds.Require` → BalanceByCurrency,
  7 ms for 18.6k rows) while holding the lock. Correctness-motivated, but it serialises payments per account and
  blocks concurrent transaction INSERTs on that account (FK `FOR KEY SHARE` waits up to 47 ms in pgss).
- Auth: refresh is faster on the branch (−29% p50, −65% p95); login unchanged.
- Robustness: **improved**. Under 100 concurrent dashboard-summary requests main served **0** (pool deadlock);
  the branch served 1,703 (p50 743 ms, degraded but alive). The feature-gate deadlock exists in both.
- Resources under the same mixed load (300 req/s, 30 s window, `results/profile/*-mixed-300`):

| per request | branch | main | Δ |
|---|---:|---:|---:|
| Go CPU | 0.61 ms | 0.54 ms | +13% |
| heap allocations | ~1,020 allocs / 54 KB | ~580 allocs / 39 KB | +75% / +39% |
| Postgres exec time (whole run) | 81.4 s | 65.8 s | +24% (12.4 s = correct name sort; 5.5 s = funds checks) |
| GC | 34 GCs, 1.5 ms pause / 30 s | 25 GCs, 1.2 ms | negligible |

- Micro-benchmarks (`results/bench-*.txt`, medians): `money.Amount` JSON marshal 1.25 µs/8 allocs vs float64
  0.65 µs/2; `Scan` 0.59 µs/5 allocs vs 0.10 µs/0; `Sum` of 1,000 280 µs/2,004 allocs vs 1.2 µs; encode 100-row
  page: same time (≈250–300 µs) but 502 vs 3 allocs. Handler (fake repo, gin, JSON): list 100 rows 505 µs / 640 allocs
  vs 424 µs / 141 (+19%); list 20 rows 127 vs 116 µs; create 66 vs 46 µs. The RLS response buffer adds 2 allocs and
  ~+50% bytes, no measurable time (in-memory bench), 7.8% of alloc bytes / 1.5% CPU under load.
  Full per-request RLS overhead vs a pool-only query (real DB, single-threaded): 591 vs 289 µs with lib/pq default.
- SSE (`results/sse/`): 1,000 open `/notifications` streams cost the branch 4.4 goroutines and ~68 KB RSS each
  (main 3.4 / ~52 KB; +1 heartbeat goroutine), 0 DB connections, no effect on a 50 rps probe (p95 1.42 vs 1.36 ms).

## 4. Where the time goes (branch, mixed 300 req/s)

Go is not the bottleneck: 5.5 s CPU in 30 s at 300 req/s (≈0.18 core). Top CPU: syscalls/network to Postgres 34%,
scheduler 20%, lib/pq extended-protocol `prepareTo` (2 round trips per parameterised query) **13.6%**, JSON 8%,
`shopspring/decimal` 4.5% (12.5% of alloc bytes), response buffering 1.5% (7.8% of alloc bytes), go-cache
`Items()` copy on every write 1.6% of alloc bytes, JWT 2.7%. Every authenticated request does ≥4 extra round trips
before business SQL (auth `FindUserById` on the pool, `BEGIN`, `set_config` ×2 RT, `COMMIT`).

Postgres is the bottleneck: top statements by total time (`profile/branch-mixed-300/pgss_total.csv`; plans in
`explain-branch.txt`, heavy user):

| # | statement (caller) | share of DB time | mean / max ms | heavy-user plan |
|---|---|---:|---:|---|
| 1 | account balances `SUM … GROUP BY account_id` (`accountRepository.go:112`, called by GET /account **and** every dashboard-summary `analyticsService.go:195`) | 36.1% | 5.1 / 23.6 | Seq Scan 51.7k rows, 21.8 ms |
| 2 | category expenses all-time (`analyticsRepository.go:92`) | 19.9% | 8.5 / 31.5 | Seq Scan 42.5k rows + hash join, 29.2 ms |
| 3 | transaction page `ORDER BY transaction_name, id LIMIT/OFFSET` (`transactionRepository.go:528`) | 15.2% | 4.5 / 21.9 | Parallel Seq Scan + top-N sort, 14.9 ms (main: 0.16 ms because it ignores the sort) |
| 4 | budget spent this month, `date_trunc('month', created_at) = …` (`transactionRepository.go:253`) | 10.6% | 3.5 / 21.1 | non-sargable: bitmap over 35.6k budget rows, 12.5 ms |
| 5 | balance by currency under `FOR UPDATE` (`funds.Require`) | 5.5% | 6.3 / 10.9 | 18.6k rows, 7.0 ms |
| 6 | `COUNT(*)` for every list request, before the cache lookup (`transactionService.go:238`) | 1.7% | 0.5 / 2.7 | index-only, 2.0 ms |
| 7 | `INSERT INTO transactions` (+ audit trigger) | 1.5% | 0.3 / **47.4** | max = FK `FOR KEY SHARE` waiting on the payment's `FOR UPDATE` |
| 8 | dashboard category expenses in range | 1.4% | 0.4 | index scan, 1.2 ms |
| 9 | monthly summary in range | 1.3% | 0.4 / 2.6 | 1y: Seq Scan 21 ms |
| 10 | `SELECT … FROM account … FOR UPDATE` (`accountRepository.go:169`) | 1.3% | 1.4 / **62.5** | lock waits |
| – | auth `FindUserById` (`userRepository.go:157`) | 0.9% | 0.03 | 24,001 calls = 1 per request, selects the bcrypt hash too |

Missing indexes / query shapes (tested inside rolled-back transactions, `index-experiments-branch.txt`):

| fix | before → after |
|---|---|
| Q4 rewrite: `created_at >= date_trunc('month', now()) AND created_at < … + 1 month` (no new index) | 12.5 → 1.8 ms |
| index `(user_id, type_transation, transaction_name, id)` for name-sorted pages | 14.9 → 0.9 ms (page 25), 0.06 ms (page 1) |
| covering `(user_id, account_id) INCLUDE (type_transation, amount, currency)` for balances | 21.8 → 12.3 ms |
| same index for the funds check | 7.0 → 3.7 ms |

RLS policy cost (`rls-cost.txt`, policies enforced vs bypassed): balances 29.7 vs 19.9 ms (+50%) because
`current_setting()` is evaluated per row; EXISTS-join policies (card_balances) 0.19 vs 0.03 ms.
No N+1 found in the hot read paths (budgets/accounts aggregate in one query); the remaining fan-out is serial
ownership/lookup queries in the write paths (create tx = 7 statements, card payment ≈ 12) and the frontend
dashboard paging through *all* of the month's transactions 100 at a time (5 sequential calls for the heavy user).

## 5. Ranked improvement opportunities

| # | change | where | expected impact | effort |
|---|---|---|---|---|
| 1 | Fix the pool deadlock: evaluate feature flags through the request tx (`txhelper.FromContext`) or before `RLSMiddleware`, and cache flags in-process (TTL 30–60 s); add a pool-acquire timeout and `idle_in_transaction_session_timeout` as a safety net | `featureflag.go:12/69`, `rls.go:58` | removes permanent outage at ≥25 concurrent gated requests; −1 query/request on gated routes | S |
| 2 | Stop recomputing balances from the full ledger on every read: maintain `account.balance` (or a per-account/currency balance table) in the same tx as each write; meanwhile add the covering index | `accountRepository.go:112`, `analyticsService.go:195`, `funds.go:56` | −36% DB time under the mixed load (−42% incl. funds checks); /account and dashboard-summary ~20 ms → ~2 ms for heavy users; ~1.8× with the index alone | M (index: S) |
| 3 | Card payments: `FOR NO KEY UPDATE` instead of `FOR UPDATE`, and an O(1) funds check (#2) | `accountRepository.go:169`, `creditcardService.go:348–380` | removes 47–62 ms FK lock waits on concurrent inserts; payment p50 15 → ~6 ms | S |
| 4 | Sargable month filter in budget-spent queries | `transactionRepository.go:208, 253` | 12.5 → 1.8 ms; −10% DB time | S |
| 5 | Index `(user_id, type_transation, transaction_name, id)` (and/or keyset pagination) | migration | name-sorted pages 14.9 → 0.9 ms; −15% DB time under writes | S |
| 6 | Pre-aggregate all-time analytics (monthly rollup table or materialized view refreshed on write / short TTL cache keyed per user) | `analyticsRepository.go:92, 143` | category-expenses 29 ms, monthly-summary 40 ms → <2 ms; −20% DB time | M |
| 7 | `binary_parameters=yes` (or move to pgx) — currently forced off | `config.go:806` | 1 round trip instead of 2 per parameterised query; bench −20% per RLS request (591 → 464 µs); −13% Go CPU | S (verify `[]byte`/numeric params) |
| 8 | Cache the auth user lookup (short TTL LRU, drop `password` from the SELECT) or fold it into the RLS tx | `auth.go:84`, `userRepository.go:157` | −1 pool checkout + 2 RT per request; also lowers deadlock pressure | S |
| 9 | RLS policies: wrap `current_setting(...)` in `(SELECT …)` so it becomes an InitPlan | migration | −30–50% on large scans when RLS is enforced | S |
| 10 | Transaction list: check the cache before `COUNT(*)`; replace go-cache `Items()` scan in `DeleteByPrefix` with per-user key sets/generation counter | `transactionService.go:238`, `cache.go:39` | −1 query per cached list; O(1) invalidation | S |
| 11 | Frontend dashboard: use a summary endpoint instead of paging all month transactions (5+ sequential calls) | `FrontendNextjs/gestor/app/repository/transactionRepository.ts:67` | dashboard TTFB −30–50% for heavy users | S–M |
| 12 | Reduce decimal allocations on hot paths: scan NUMERIC into `decimal.NullDecimal`/int64 cents for aggregates; pool the RLS response buffer (`sync.Pool`, pre-size) | `money.go:333`, `rls.go:84` | −40% allocs/request (back toward main), few % CPU | S–M |
| 13 | Budget alert goroutine: runs on the pool with `context.Background()` *before* the request commits (misses the new row; outside RLS) — run after commit, bounded | `transactionService.go:111` | correctness + one less pool checkout per bill | S |
